# X11 / NeoMagic — root cause, fix, and the acceleration reality

## The "undefined symbol" load failure — root cause (and it is NOT a neomagic bug)

On the ThinkPad 600X the GPU is a **NeoMagic MagicGraph256ZX (NM2360)** — a 1998-era
2D chip with ~4 MB VRAM. It has **no DRM/KMS driver** in the kernel; the real
600X uses the legacy `xf86-video-neomagic` DDX, with `vesa`/`fbdev`/modesetting
available as the QEMU fallback paths.

At first the legacy drivers failed to load in Xorg 21.1.x with:

```
(EE) Failed to load .../neomagic_drv.so: undefined symbol: vgaHWFreeHWRec
(EE) Failed to load .../vesa_drv.so:     undefined symbol: VBESetModeParameters
(EE) Failed to load .../fbdev_drv.so:    undefined symbol: fbdevHWSave
```

**Root cause — Buildroot hardening, not the driver.** Buildroot's default
`BR2_RELRO_FULL=y` injects `-Wl,-z,now` (BIND_NOW) into every link. Xorg's DDX
drivers are, by design, built with **no `DT_NEEDED`** on the helper modules
(`libvgahw.so`, `libint10.so`, `libfbdevhw.so`) and instead resolve them lazily
at runtime via `xf86LoadSubModule()` (the server dlopens modules with
`RTLD_LAZY|RTLD_GLOBAL`). Under `-z now`, glibc resolves **all** symbols eagerly
at `dlopen()`, before the helper modules are in the global scope — so `dlopen`
fails before the driver ever runs.

This is exactly the classic "hardened toolchain × legacy X driver" failure,
documented upstream for years:
- Gentoo hardened bug **#394757** (`undefined symbol: vgaHWFreeHWRec`)
- freedesktop **#41208** (workaround = pre-load the sub-modules in `xorg.conf`)
- Debian **#1095682** (same signature; Debian's answer: "use modesetting")

`xf86-video-neomagic` 1.3.1 itself **compiles cleanly** against xorg-server 21.x —
the failure is purely the runtime load, not a source-level incompatibility.

## The fix used by this image (no driver fork/PR needed)

The actual workaround is runtime-only: pre-load the helper sub-modules in `xorg.conf`
so their symbols are already in the global scope before the legacy DDX is `dlopen`'d:

```ini
Section "Module"
    Load "vgahw"
    Load "int10"
    Load "fbdevhw"
    Load "shadow"
    Load "shadowfb"
EndSection
```

This keeps Buildroot's full RELRO hardening enabled. No `BR2_RELRO_PARTIAL` or
per-driver linker change is applied in this tree; the preload is the workaround that
is actually present so the legacy NeoMagic DDX can find its helper symbols. No source
patch is included. Hardware validation on the physical 600X is still pending, as
recorded in `docs/adr/ADR-004-display-x11.md`.

## Input

This image uses devtmpfs + mdev, not udev, so `xf86-input-evdev` is not used.
`configs/thinkpad600x_defconfig` selects the external Buildroot packages
`package/xf86-input-mouse` and `package/xf86-input-keyboard`; they build
`mouse_drv.so` and `kbd_drv.so` for the image. The old prebuilt module files are
not kept in the rootfs overlay.

`xorg.conf` binds the classic `kbd` driver as `CoreKeyboard` and the classic
`mouse` driver to `/dev/input/mice` as `CorePointer` for the PS/2 TrackPoint. The
kernel-side input support is `CONFIG_MOUSE_PS2`, `CONFIG_INPUT_MOUSEDEV`, and
`CONFIG_KEYBOARD_ATKBD`.

## Hardware acceleration — corrected finding (the earlier "not available" claim was wrong)

**Correction.** The NeoMagic MagicGraph 256ZX *does* have a real 2D BitBLT engine,
and the Linux 6.12.104 kernel used by this image includes the corresponding
`neofb` acceleration path. `drivers/video/fbdev/neofb.c` declares, for the NM2360:

```c
info->flags |= FBINFO_HWACCEL_IMAGEBLIT |
               FBINFO_HWACCEL_COPYAREA |
               FBINFO_HWACCEL_FILLRECT;
```

i.e. the kernel path accelerates **solid fill, screen-to-screen blit, and host-to-video
mono expansion** (font/glyph rendering) by programming the chip's registers directly.
The source also defines hardware-cursor registers, but the kernel cursor code is
commented out; cursor handling is not an active acceleration path. The register map
and the exact programming sequences are public (GPL) in `include/video/neomagic.h` +
`neofb.c`, and mirrored by the X.Org driver `xf86-video-neomagic` (`neo_reg.h`,
`neo_2200.c`). Full details:
`docs/NEOMAGIC.md`, `docs/NEOMAGIC_REGISTER_MAP.md`.

What *was* removed is **XAA** (the XFree86 acceleration *software* API) from
xorg-server 1.13 (2012). That removed the *X11-side* acceleration backend, not the
chip's capability. The consequence is narrower than previously stated:

- The **Linux console** path is configured through `neofb`; its acceleration
  implementation is present in the kernel, but operation on the physical 600X is
  still unverified.
- The **X11/CDE path** does the drawing in userspace (the `neomagic`/`fbdev` DDX
  uses `shadowfb`) and therefore does *not* reach the BLT engine — this is the gap
  to close, not the hardware.
- Re-exposing the engine under X11 is a *driver* task, not a hardware task: add an
  EXA backend to `xf86-video-neomagic` that programs the same BAR1 registers (EXA
  still ships in xorg-server 21.x), or restore XAA. See `docs/NEOMAGIC_ACCELERATION.md`.

The repository contains no NeoMagic emulator validation, so accelerator validation
still requires the physical 600X; QEMU remains used for software/modesetting
integration only.

## NeoMagic diagnostic build

`package/neomagic-diag` builds `tools/neomagic_diag/neomagic_diag.c` with
`$(TARGET_CC) $(TARGET_CFLAGS) -static` and installs the result as
`/usr/bin/neomagic_diag`. For a standalone cross build, use the Buildroot toolchain
prefix:

```sh
make CROSS_COMPILE="$HOME/br2-out/host/bin/i686-buildroot-linux-gnu-"
```

## On Rust for this

The affected stack (`xorg-server`, `xf86-video-neomagic`, `neofb`) is **C**, and the
acceleration work is a C driver change (register programming recovered from GPL
sources). Rust is optional for user-space diagnosis tooling only. The load-failure fix
above is a configuration-only change, not a source patch.
